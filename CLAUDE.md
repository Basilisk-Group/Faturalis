# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

This repo currently contains a single project, **qr-bench**, in `qr-bench/`. All commands below assume `cd qr-bench` first.

qr-bench is a local measurement tool (not a product) for how reliably Portuguese fiscal QR codes — the ones printed on invoices/receipts per AT/SAF-T rules — can be extracted from real-world images and PDFs.

## Commands

Dependency management is via `uv` (not pip/poetry).

```bash
uv sync                                          # install deps into .venv
uv run uvicorn qr_bench.main:app --reload        # run the app at http://127.0.0.1:8000
uv run pytest                                    # full test suite
uv run pytest tests/test_parser.py               # single file
uv run pytest tests/test_nif.py::test_valid_nifs_pass_checksum  # single test
uv run python scripts/generate_samples.py        # regenerate ./samples + ground_truth.json
docker compose up --build                        # run containerized (see Docker section below)
```

System dependency: `pyzbar` binds to the `zbar` shared library, which must be installed via the OS package manager (`pacman -S zbar`, `apt install libzbar0`, `brew install zbar`) — it is not a Python package and `uv sync` cannot install it. Not needed if you're only running via Docker; the image installs it.

**Always run `uv run pytest` before declaring any code change in this repo done**, even a small or seemingly unrelated one, and report the result.

No lint/format tooling is configured in this repo.

## Architecture

### Pipeline flow (`qr_bench/pipeline.py`)

`process_file(path, source, display_name)` is the single entry point used by both the upload endpoint and the inbox watcher. PDFs are rasterized page-by-page via `pdf_utils.rasterize_pdf` (PyMuPDF, 300 DPI) before each page goes through the same per-image path as a plain image upload. Each page/image independently runs: `decode.decode_qr` → `parser.parse_qr_string` → `db.find_first_by_atcud` (dedup lookup) → `flags.evaluate_flags` → `flags.initial_status` (lifecycle status) → client attribution by field `B` → thumbnail generation → `db.insert_document` → `suppliers.schedule_lookup`. A single multi-page PDF produces multiple DB rows (one per page, `page_number` set).

### Decode strategy (`qr_bench/decode.py`)

Ordered, first-success-wins: `pyzbar:original` → `opencv:original` → for each of `grayscale`/`upscale2x`/`adaptive_threshold`/`rotate90`/`rotate180`/`rotate270`, try `pyzbar:<variant>` then `opencv:<variant>` (`decode.TOTAL_ATTEMPTS` = 14, the max possible). The winning attempt's name is stored verbatim as `strategy` and drives the dashboard's "decoded first attempt" vs "needed preprocessing" stats (`db.FIRST_ATTEMPT_STRATEGIES`).

**"No QR present" vs "decode failed" is a real distinction, not just a UI label.** OpenCV's `QRCodeDetector.detectAndDecode` returns corner points independently of whether it decodes the text, so `qr_pattern_detected` is tracked separately from `decode_success` across *every* attempt. If no attempt across all 14 tries ever detects a pattern, `flags.evaluate_flags` raises `SEM_QR`; if a pattern *was* detected but nothing ever decoded, it raises `QR_ILEGIVEL` instead — a different, more specific failure than "nothing there at all." Ground-truth marking (`no_qr` label) lets the dashboard report the `qr_pattern_detected` heuristic's actual accuracy (`db.compute_stats`'s `no_qr_heuristic_accuracy`).

`ocr_fallback.py` is an intentional stub (`raises NotImplementedError`) — OCR is a non-goal and nothing calls it.

### Parsing (`qr_bench/parser.py`)

`parse_qr_string` splits on `*`, then each part on the **first** `:` only (values can contain other punctuation). Fields are looked up by key everywhere downstream — `I2`..`I8` (tax bases/VAT per rate) and `P` (retenção na fonte) are optional and must never be assumed present or positional.

### Flag registry (`qr_bench/flags.py`) — the single source of truth for every user-facing observation

`FLAGS` is a dict of 16 codes (e.g. `TOTAIS_INCONSISTENTES`, `NIF_EMITENTE_INVALIDO`), each with `severity` (`erro`/`aviso`/`info`), a 3-5 word `label_pt`, and `explanation_pt`/`cause_pt`/`action_pt` — all Portuguese-from-Portugal prose, no English variants (unlike the rest of the UI chrome, which is bilingual; flag copy is intentionally PT-only). `GET /api/flags` returns this dict verbatim — **the frontend and `/glossario` never hardcode flag text**; if you add a flag, its copy lives only in this dict.

`evaluate_flags(fields, *, decode_success, qr_pattern_detected, max_decode_attempts, dedup_match)` is a **pure function** — plain data in, `list[{"code": ..., "detail": {...}}]` out, no DB access — that decides which codes fire for one document. This is what actually replaced the old ad-hoc `validate.validate_fields`; `validate.py` now only holds the low-level primitives `evaluate_flags` composes (`nif_checksum`, `validate_date`, `amounts_equal`, `parse_amount`, `RATE_TABLES`/`RATE_BRACKETS`/`rates_for_region`). Being pure is what makes `tests/test_flags.py` able to test 15 of the 16 codes without touching the database.

Two things `evaluate_flags` deliberately does NOT decide:
- **Dedup vs. conflict** (`DUPLICADO` / `DUPLICADO_CONFLITUOSO`): `pipeline.process_image` looks up the earliest row with the same `H` (ATCUD) via `db.find_first_by_atcud` and passes it in as `dedup_match`; `evaluate_flags` compares `O` (document total) via `amounts_equal` — same total → `DUPLICADO`, different total → `DUPLICADO_CONFLITUOSO` (never silently deduped). `pipeline.py` derives the `duplicate_of` column value straight from whichever of those two fired, rather than re-running the comparison.
- **`FORNECEDOR_DESCONHECIDO`**: can't be known at flag-evaluation time because the VIES lookup it depends on runs asynchronously *after* the row already exists (see Supplier lookups below). It's decided separately, at **read time**, by `flags.evaluate_supplier_flag()` — called from `db._row_to_dict` using the already-joined `supplier_status`/`field_a` columns — and appended to the flags list on every `GET`, never persisted. A `not_registered`/`error`/`disabled` supplier status means "unknown"; `found`/`found_no_name` do not trigger it.

Storage is minimal by design: only `{"code": ..., "detail": {...}}` goes into `validation_flags_json` (`detail` holds the specific numbers for that document, e.g. `{"bases": ..., "total": ...}`). The human-readable, value-interpolated message (e.g. *"Bases (3,25 €) + imposto (0,75 €) = 4,00 €, mas o documento indica 4,50 €."*) is rendered fresh on every read via `flags.render_message(code, detail)` — templates live in `explanation_pt` as `{key}`-style Python format strings matched to `detail`'s keys. `db._row_to_dict` enriches each stored flag with `message` and `severity` before it ever reaches the API; PT number formatting (`3,25 €`, comma decimal, `€` suffix) comes from `flags.format_eur_pt`/`format_pct_pt`/`format_date_pt` — reuse those rather than formatting amounts ad hoc anywhere new.

**VAT rates are region-aware, not a flat assumption.** `validate.RATE_TABLES` maps `I1` (tax region: `PT`/`PT-MA`/`PT-AC`) to its own reduced/intermediate/normal rates (mainland vs. Madeira vs. Açores genuinely differ), selected via `rates_for_region()` and defaulting to mainland `PT` when `I1` is missing/unrecognized — mismatches raise `TAXA_IVA_ATIPICA`. `validate.RATE_BRACKETS` (which `I3`/`I4` etc. pair maps to which rate name) is imported directly by both `flags.py` and `scripts/generate_samples.py` so nothing can define a second, drifting copy of that mapping or the rate table itself — don't reintroduce one.

`E == "A"` (anulado) both sets the `cancelled` column on the row (used by `db.compute_stats` to exclude cancelled docs from ground-truth accuracy) *and* raises `DOCUMENTO_ANULADO` — these are two independent, deliberately redundant signals derived from the same one-line check; the column feeds stats plumbing, the flag feeds the user-facing registry/UI.

### Accountant workflow: clients, lifecycle, corrections, export

qr-bench has two front ends now. `/bench` (`static/index.html`, unchanged) is the internal benchmark dashboard — decode strategy, timing, ground-truth marking. `/` and `/clientes/{id}` (`static/clientes.html`, one file handling both the client list and client detail views via client-side routing on `window.location.pathname`) is the accountant-facing workflow, and deliberately never shows decode strategy/timing/ground-truth controls.

**Client attribution** (`pipeline.py`, `db.get_or_create_client`): a document's client is resolved from field `B` (acquirer NIF) at ingestion time. `B == "999999990"` (consumidor final) or an absent `B` leaves `client_id` null — these show up as a synthetic "unattributed" bucket in the UI (`id: null` in `GET /api/clients`, routed as `/clientes/unattributed`), never as a real client row. A NIF is auto-created as a client named after the NIF itself (`db.get_or_create_client`) the first time it's seen; renaming is a separate explicit action (`PATCH /api/clients/{id}`) that never happens automatically. Client attribution does not check NIF checksum validity - an invalid-but-present NIF still groups documents together (and separately raises `NIF_ADQUIRENTE_INVALIDO`).

**Lifecycle status** (`documents.status`, one of `recebido`/`extraido`/`a_rever`/`validado`/`exportado`): decided once at ingestion by `flags.initial_status(decode_success, flag_entries)` — undecodable stays `recebido`, any `erro`/`aviso` flag routes to `a_rever`, otherwise `extraido`. From there, three actions resolve a document: `POST /api/documents/{id}/validate` (accept as-is → `validado`), `POST /.../correct` (see Corrections below, also → `validado`), `POST /.../reject` (stores a reason → back to `a_rever`, never a dead end). `POST /api/clients/{id}/bulk_validate` (or `.../unattributed/bulk_validate`) validates every *currently* `extraido` document for that client in one UPDATE — it does not touch `a_rever` documents, so a bulk validate can't accidentally wave through something flagged. `POST /api/export` is the only path to `exportado`, and re-exporting an already-`exportado` document is allowed and just refreshes `exported_at` (see Export below).

**Corrections** (`corrections` table, `db.record_corrections`/`get_corrections`/`get_effective_fields`): a document's `field_*` columns and `all_fields_json` are the original decode/parse output and are **never** written to again after `insert_document`. A correction inserts one audit row per changed field into `corrections`, with `original_value` set to whatever the *effective* (not necessarily the true original) value was immediately before this edit — so a second correction to the same field shows a proper before/after diff against the first correction, not a re-statement of the decode output. `db.get_effective_fields(doc)` merges the latest correction per field on top of `all_fields` and is attached to every document as `doc["effective_fields"]` by `_row_to_dict` itself (not just in the export path) — anything that should reflect the corrected value (the accountant table's Total column, the correction dialog's pre-fill, export rows) reads `effective_fields`, not `field_o`/`all_fields` directly. Get this wrong and a correction silently doesn't show up anywhere except the audit log.

**Export** (`qr_bench/exporter.py` + `qr_bench/export_presets.py`): pure formatting, no DB access — callers must pass documents that already carry `effective_fields` (which, per above, they always do). `export_presets.PRESETS` is a plain dict (`{"generico": {"label_pt": ..., "columns": [...]}}`) exposed via `GET /api/export/presets` so the frontend dropdown is never hardcoded; adding an ERP-specific preset (Primavera, Sage, PHC, TOConline) later is a new dict entry, not a code change. CSV is UTF-8 with a BOM + semicolon delimiter + comma-decimal numbers (`exporter.format_number_pt`, no thousands separator, kept deliberately plain for accounting-software import) — PT locale throughout, unconditionally, not tied to the PT/EN UI toggle (exports are always Portuguese, like flag text). XLSX uses native `openpyxl` numeric/date cell types with PT-style `number_format` strings rather than pre-formatted text, so Excel's own locale renders them; it always gets a second "Documentos Sinalizados" sheet built from whichever exported documents have flags, pulling `cause_pt`/`action_pt` straight from the flag registry. `db.mark_exported(doc_ids)` runs after the file is built, unconditionally flipping every included document to `exportado` regardless of its prior status — exporting with "include unvalidated" checked will happily export (and then mark-exported) an `a_rever` document if you ask it to; that's accepted as-is per the single-status-field model rather than adding a parallel "has been exported" boolean.

### Storage (`qr_bench/db.py`)

Plain `sqlite3`, no ORM. The `documents` table holds every decode attempt (success or failure); a separate `suppliers` table (see below) is cached by NIF and left-joined into `documents` reads. JSON-valued columns (`tax_details_json`, `all_fields_json`, `validation_flags_json`) are stored as JSON text and transparently decoded/encoded at the `db.py` boundary (`_row_to_dict` strips the `_json` suffix on read, and is also where flag enrichment + the dynamic `FORNECEDOR_DESCONHECIDO` flag get added — see Flag registry above). `config.DB_PATH` is read dynamically at call time inside `get_connection()`, which is what makes it monkeypatchable per-test (see Testing below) without any dependency injection machinery.

Schema changes ship as entries in `db.MIGRATIONS` (`[(column_name, ddl_type), ...]`), applied via `_ensure_columns()`'s `PRAGMA table_info` + `ALTER TABLE` on every `init_db()` call — this is on top of (not instead of) adding the column to `SCHEMA` itself, so both a fresh DB and an existing local dev DB end up with the same shape. Add new columns to *both* places.

### Supplier lookups (`qr_bench/suppliers.py`)

`pipeline.process_image` calls `suppliers.schedule_lookup(nif)` right after `db.insert_document` — this only enqueues onto an in-process `queue.Queue` (or, if `config.VIES_ENABLED` is false, synchronously caches a `disabled` status with zero network activity), so ingestion never blocks. A daemon worker thread (started alongside the inbox watcher in `main.py`'s `lifespan`) drains the queue and calls the real VIES REST API (`ec.europa.eu/taxation_customs/vies/rest-api/ms/PT/vat/{nif}`, timeout from `config.VIES_TIMEOUT`), caching every outcome — including failures — in the `suppliers` table so a given NIF is never looked up twice.

**`not_registered` and `error` are deliberately different statuses, not both "unknown."** VIES only lists businesses registered for intra-EU trade, so a purely domestic supplier (a local café, a shop that never invoices across a border) legitimately comes back `isValid: false` even with a perfectly valid NIF — that must never be displayed as if something's wrong with the document. Only a real network failure/timeout becomes `error` (shown as "unknown" in the UI); a definitive not-registered answer is shown as "not found in VIES". Don't conflate either with `NIF_EMITENTE_INVALIDO` (the local mod-11 checksum flag) — unrelated signals about unrelated things. All three of `not_registered`/`error`/`disabled` feed into the `FORNECEDOR_DESCONHECIDO` flag identically (see Flag registry above); `found`/`found_no_name` do not.

Because nothing consumes the lookup queue unless `suppliers.start_supplier_worker()` was actually started (i.e. only when uvicorn runs the real app via `main.py`'s lifespan), tests never make real network calls just by calling `pipeline.process_image` — `schedule_lookup` is a pure enqueue in the default (network-enabled) test config. Tests that need to exercise the VIES response-parsing logic monkeypatch `suppliers.fetch_vies` or `urllib.request.urlopen` directly (see `tests/test_suppliers.py`).

### Ingestion paths

Two entry points feed the same `pipeline.process_file`: `POST /api/upload` (persists each upload permanently under `config.UPLOAD_DIR` with a UUID filename — not a tempfile, so the Docker `qrbench-uploads` volume actually holds something — then calls `process_file` with `display_name` set to the original filename) and `watcher.py` (a daemon thread polling `./inbox` every `config.INBOX_POLL_INTERVAL_SECONDS`, moving handled files to `inbox/_processed/` so they aren't reprocessed — started/stopped via FastAPI's `lifespan` in `main.py`, alongside the supplier lookup worker). `GET /health` checks DB connectivity and that `pyzbar` still imports; it's what the Docker `HEALTHCHECK` polls.

### Frontend

Three static pages, no build step, no framework, each vanilla JS:
- `static/index.html` at `GET /bench` — the internal benchmark dashboard. Polls `/api/stats` and `/api/documents` every 2s, inline-SVG bar chart for decode-strategy counts (no chart library). Row expansion, ground-truth marking, CSV export.
- `static/clientes.html` at `GET /` and `GET /clientes/{id}` — the accountant workflow (see Accountant workflow above). One file for both list and detail views: `parseRoute()` reads `window.location.pathname` (`/clientes/(.+)` → detail for that id or `"unattributed"`, else list) and `navigateToClient()` does `history.pushState` + re-render rather than a real navigation. Polls every 4s (slower than `/bench`'s 2s - this view is edited via modals more than watched passively). Never renders decode strategy, timing, or the Correto/Errado/Sem-QR ground-truth buttons - those are `/bench`-only by design.
- `static/glossario.html` at `GET /glossario` (linked from both other pages) — renders `GET /api/flags` as standalone reference documentation. Deliberately a separate page, not a client-side "view" folded into either dashboard.

The UI chrome (headings, buttons, column labels, status badges) is bilingual (PT-PT default, EN toggle, persisted in `localStorage` under the same `qrbench_lang` key across all three pages, so the choice carries over on navigation): static markup carries `data-i18n="key"` populated by `applyStaticText()`, dynamic strings go through `t(key, ...args)` against each page's own `I18N` dict (duplicated per file, not shared - consistent with the no-build-step constraint). **Flag badges/popovers and every export are the exceptions — always Portuguese regardless of the toggle**, per the Flag registry and Export sections above. A flag badge is colored by `sev-erro`/`sev-aviso`/`sev-info`; clicking (or hovering, with a short close delay) opens a popover built from `flagRegistry[code].label_pt/cause_pt/action_pt` plus that specific flag instance's already-interpolated `message` — see `flagBadges()`/`openFlagPopover()` (duplicated near-identically in both `index.html` and `clientes.html`). Popovers close on outside click and on every table re-render.

`clientes.html`'s document table always shows the raw QR string **collapsed** behind a `<details>`/`<summary>` toggle, never expanded by default - the effective/corrected fields and correction history are what's shown up front. Native `<input type="checkbox">`/`<input type="radio">` get `accent-color: var(--accent)` (see the export dialog's "Incluir não validados" checkbox) so they don't render as the browser's default light-colored control against the dark theme. The documents table has `min-width: 900px` with `.actions { flex-wrap: nowrap }` specifically so the action buttons never wrap onto a second line at narrow widths - a wrapped row was previously taller than its neighbors, which visibly broke the horizontal row-divider alignment; the panel's existing `overflow-x: auto` handles narrow viewports by scrolling instead.

### Docker

Multi-stage `Dockerfile`: a `builder` stage installs Python deps with `uv` in their own layer (cached separately from app source — deps only reinstall when `pyproject.toml`/`uv.lock` change, not on every source edit), then a `python:3.11-slim` runtime stage with `libzbar0`/`libglib2.0-0`/`libgomp1` (the actual runtime needs of `pyzbar` + `opencv-python-headless` — **must** stay `opencv-python-headless`, not `opencv-python`, or it pulls in X11/GUI libs that don't exist in a slim image), running as a non-root `qrbench` user (UID 1000, chosen to match a typical host user for the `./inbox` bind mount). `uv` itself is installed via `pip install uv` in the builder, not `COPY --from=ghcr.io/astral-sh/uv`, because `ghcr.io` isn't reachable from every build network (learned the hard way — `docker.io` worked, `ghcr.io` didn't).

`docker-compose.yml` runs one service, with named volumes for `/app/data` (the sqlite DB) and `/app/uploads`, and `./inbox` bind-mounted so host-dropped files reach the watcher exactly like local dev. `VIES_ENABLED=false` in compose is intentional, not a placeholder — the container must work with zero network access out of the box; flip it to `"true"` for real supplier lookups. Config env vars: `DATABASE_PATH`, `UPLOAD_DIR`, `INBOX_DIR`, `VIES_TIMEOUT`, `VIES_ENABLED` (all read in `config.py`, with local-dev defaults under the repo root when unset).

### Testing

`tests/conftest.py`'s `test_db` fixture monkeypatches `config.DB_PATH` to a `tmp_path` file per test — this works because `db.py` re-reads `config.DB_PATH` on every connection rather than capturing it at import time. `scripts/generate_samples.py` is not a package (no `__init__.py`); tests import it by inserting `scripts/` onto `sys.path` directly (see `tests/test_e2e_samples.py`). Its `generate_dataset()` and `build_qr_payload()` are the reusable, hermetic sample-generation API — the `__main__` block is just a thin CLI wrapper around them for populating `./samples` manually. `pipeline.process_image` takes a PIL `Image` directly, so pipeline-level tests (`tests/test_pipeline.py`, `tests/test_flags.py`) build a payload + render a canvas + call it in-memory without touching disk.

NIF generation for synthetic samples (`scripts/generate_samples.py::random_nif`) and NIF validation (`validate.py::nif_checksum`) implement the same mod-11 algorithm independently — if one changes, check the other stays consistent or tests will start failing for the wrong reason (bad checksums, not real pipeline bugs). VAT rates avoid this trap: the generator imports `RATE_TABLES`/`RATE_BRACKETS` from `validate.py` rather than redefining them.

**`tests/test_flags.py` enforces flag/sample completeness both ways**: `scripts/generate_samples.py::FLAG_SAMPLE_BUILDERS` maps every code in `flags.FLAGS` to a callable building a deterministic triggering sample (or, for the two dedup codes, an ordered *pair* of samples — process both in order, the flag is only expected on the second). Adding a flag to `FLAGS` without adding a builder (or vice versa) fails the suite immediately via `test_every_registered_flag_has_a_sample_builder`/`test_every_sample_builder_maps_to_a_registered_flag` — keep both in sync in the same change. `QR_ILEGIVEL`'s builder (`corrupt_qr_data_region`) doesn't rely on blur/JPEG fuzziness (which only *sometimes* breaks decoding) — it overwrites the interior ~44% of a clean QR code with noise while leaving the finder-pattern corners intact, which reliably yields `qr_pattern_detected=True, decode_success=False` (verified empirically across 10+ payload lengths at a 0.28 margin fraction).

`scripts/generate_samples.py`'s default 46-sample dataset (`generate_dataset()`) is 40 decode-difficulty samples (clean/moderate/heavy/no_qr tiers) plus 6 targeted feature samples from `generate_special_samples()` (cancelled, duplicate pair, conflicting pair, PT-MA) — a distinct, older mechanism from `FLAG_SAMPLE_BUILDERS` above; the two overlap in intent (several of the 6 feature samples also happen to trigger specific flags) but serve different tests (`tests/test_e2e_samples.py` vs `tests/test_flags.py`) and aren't deduplicated into one system.

Accountant-workflow tests (`test_clients.py`, `test_lifecycle.py`, `test_corrections.py`, `test_exporter.py`) build documents the same way (`build_qr_payload` + `render_invoice_canvas` + `pipeline.process_image`, in-memory) and then drive `db.py`/`main.py` functions directly rather than through `TestClient`/`httpx` (the project deliberately doesn't depend on those - see `tests/test_main.py`'s docstring). `main.py` route handlers are plain `async def` functions, so `asyncio.run(main.some_handler(...))` calling them directly (constructing the Pydantic payload models by hand, e.g. `main.ExportPayload(...)`) is the established pattern for endpoint-level tests. One footgun already hit once: `build_qr_payload(rng, acquirer_nif="...")` takes the NIF **literally** with no checksum correction - a fixture NIF like `"111111111"` fails the mod-11 checksum and silently adds `NIF_ADQUIRENTE_INVALIDO` (aviso → `a_rever`), which will confuse a lifecycle test expecting a "clean" `extraido` document. Use a checksum-valid literal (or `random_nif(rng)`) whenever a test's premise is "this document is clean."
